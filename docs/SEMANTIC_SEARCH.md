# Поиск мест по смыслу

`/find места, связанные с королями` — до трёх ближайших по смыслу мест из каталога Гродно. Можно искать зелень, театральную жизнь, историю образования. Ответ содержит выдержку из найденного материала, источник и Google Maps. Это кандидаты: поиск всегда ранжирует имеющиеся места, даже если точного соответствия нет. Он не проверяет все пожелания, открытие заведений и доступность посещения.

Обычный запрос «Найди места, связанные с королями» может вызвать инструмент `search_places` через облачную модель. `/find` обходит облачную модель и работает без её ключа. Поиск не изменяет порядок существующего `/walk`.

## Установка и запуск

```powershell
docker compose build bot
docker compose run --rm --no-deps bot /app/.venv/bin/python -m app.place_search
docker compose up -d bot
```

Вторая команда впервые скачивает публичную модель `intfloat/multilingual-e5-small` (около 500 МБ, нужен интернет). Она сохраняется в volume `whisper_models`, каталог `/home/bot/models/embeddings`. Не удаляй volume при обновлении. При обычном поиске загрузка из сети запрещена; отсутствие модели даёт понятную ошибку и не мешает календарю. Для запуска вне Docker: `uv sync`, затем `uv run python -m app.place_search`. Локальный кэш по умолчанию — `~/.cache/assistant-embeddings`; его можно переопределить переменной `EMBEDDING_CACHE`.

## Как устроено, в терминах Java

`SearchRequest` — DTO с валидацией. `PlaceSearch` — сервис с зависимостью `KnowledgeStore`, создаваемый один раз в `Agent`. `search()` получает карточки и только активные материалы текущего владельца, затем выполняет CPU-работу в отдельном потоке через `asyncio.to_thread` (по назначению похоже на executor). `threading.Lock` защищает модель и кэш.

1. Модель превращает название и фрагмент текста в вектор из 384 чисел — embedding. Это обученное представление смысла, а не список ключевых слов.
2. E5 получает документы с префиксом `passage: `, запрос с `query: `, включая русский язык. FastEmbed выполняет ONNX-модель на CPU, усредняет выходы токенов и нормализует вектор. Длинный текст ограничен контекстом модели; загруженные материалы уже разбиты на короткие фрагменты.
3. Скалярное произведение нормализованных векторов даёт cosine similarity. Это оценка близости, не процент уверенности.
4. Сортируем фрагменты, оставляем по одному лучшему для каждого места, выдаём первые три. Источники и координаты берём из базы, а не сочиняем моделью.
5. Векторы кэшируются в памяти по тексту. При следующем запросе новые подтверждённые материалы учитываются, удалённые исключаются; после рестарта векторы пересчитываются. Тексты остаются в PostgreSQL. Отдельная векторная БД для маленького каталога пока не нужна.

Тексты для embeddings не отправляются во внешние API. Через `/find` ответ строится локально, но доставляется Telegram. Обычный диалог по-прежнему использует OpenRouter. Пользовательские материалы не проверены редактором и в источниках обозначены явно.

Рассказчик использует гибридный поиск. Например, в вопросе «Какие правители жили в Старом замке?» harness выбирает место, и рассказчик ищет только в его карточке и подтверждённых материалах. Один список упорядочивает фрагменты по близости векторов, второй учитывает совпадения слов с большим весом для редких имён и дат. Reciprocal Rank Fusion складывает для каждого фрагмента 1/(10 + позиция) из каждого списка, где он получил совпадение. До трёх лучших фрагментов попадают в контекст рассказчика вместе с источниками. При недоступной локальной модели используется поиск по словам. Для проверки смысловых различий добавь через /learn несколько материалов об одном месте и задай вопрос своими словами.
