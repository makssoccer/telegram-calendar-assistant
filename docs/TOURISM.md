# Прогулки по Гродно и RAG-рассказчик

Первая версия: железнодорожный вокзал → главный корпус ГрГУ на Ожешко, 22 →
парк Жилибера → площадь Ленина → Советская площадь → драмтеатр → Старый замок → Новый замок.
Порядок задан каталогом. Бот не решает задачу произвольного туристического маршрута по всему городу.

## Настройка и запуск

1. Создай аккаунт на https://account.heigit.org/ и возьми Standard API key для openrouteservice.
   Официальная страница https://openrouteservice.org/ сейчас направляет туда для регистрации и управления ключами.
2. В корневой `.env` заполни `ORS_API_KEY=...`. Это отдельный ключ, не OpenRouter.
   Не отправляй ключ в Telegram или Git. `.env` исключён из Git.
3. Из каталога проекта выполни `docker compose up -d --build bot`.
   Обычный restart не перечитывает env Compose и не обновляет код внутри образа.
4. Напиши боту `/places`, затем `/walk 120`.
5. Для рассказов используется уже настроенный `OPENROUTER_API_KEY` и бесплатная модель.

`/places` не требует внешних API. `/walk` не требует LLM и Google Calendar, но требует ORS.
RAG-рассказ требует OpenRouter, но не ORS и не Google Calendar.
При недоступности ORS бот сообщает об ошибке, а не выдаёт расстояние по прямой за пеший переход.

## Как пользоваться

- `/walk 60`, `/walk 120`, `/walk 180` — бюджет в минутах, старт от вокзала, возврат не включён.
- `/walk 120 return` — включить в бюджет возвращение к вокзалу.
- «Построй прогулку по Гродно на полтора часа от университета» — через harness.
- «Построй прогулку на 2 часа с возвращением на вокзал».
- «Расскажи про Старый замок»; «Почему парк называется именем Жилибера?».
- «Сколько стоит билет в Новый замок сегодня?» — база не содержит цен; рассказчик должен признать отсутствие данных.

Можно отправлять те же запросы голосом: локальный Whisper превращает их в текст для существующего harness.
Ответ рассказчика пока текстовый, без синтеза речи.

У каждого перехода теперь есть ссылка Google Maps с указанными началом, концом и пешим режимом.
Обратный переход получает свою ссылку, если включён возврат. Ссылки соответствуют реально выбранным
остановкам, в том числе в сокращённом маршруте. Google рассчитывает путь самостоятельно, поэтому
его расстояния и время могут отличаться от ORS. Новый ключ Google или платный Maps API не нужен.
Формат ссылок: https://developers.google.com/maps/documentation/urls/get-started

## Где здесь harness

`app/agent.py` получает запрос и предлагает модели каталог инструментов:

| Инструмент | Ответственность |
|---|---|
| `list_places` | Вернуть разрешённые места и их ID |
| `plan_city_walk` | Проверить DTO, запросить пешие переходы, проверить бюджет и отформатировать план |
| `tell_place_story` | Извлечь источники для места, передать их модели, проверить ссылки в ответе |

Модель выбирает инструмент и его аргументы. Harness проверяет аргументы Pydantic-моделью,
вызывает только разрешённый Python-метод, ограничивает число запросов и время выполнения,
сохраняет результат в существующую историю PostgreSQL. Календарные инструменты продолжают работать.
У новых инструментов нет права создавать встречи или отправлять приглашения.

План маршрута возвращается пользователю непосредственно из Python. Это принципиально:
повторная генерация моделью могла бы изменить числа и снова нарушить бюджет.
Рассказ получает отдельный контекст без календаря и истории чата. Его дополнительный запрос
входит в общий лимит четырёх обращений к модели и 150 секунд на ответ.

## Расчёт маршрута

`app/walking.py` обращается к `POST /v2/matrix/foot-walking` OpenRouteService.
Координаты передаются как долгота, широта. В ответе нужны длительности в секундах и расстояния
в метрах. `null` означает отсутствие перехода, а не нулевое время.
Документация: https://giscience.github.io/openrouteservice/api-reference/endpoints/matrix/

`app/walk_planner.py` перебирает остановки в заданном порядке. Для каждого добавления проверяет:

`пешие переходы + осмотр + обратный переход (если выбран) + 10 минут запаса <= бюджет`.

Каждый переход округляется вверх до минуты, поэтому сумма показанных пользователю переходов
совпадает с итогом. Из матрицы берётся именно направление A → B, обратный путь может отличаться.
Если точка не помещается, планировщик рассматривает следующие; возвращаться к пропущенным
ранним точкам не будет. Пропущенные места перечисляются явно. Это простой алгоритм,
а не поиск оптимума. Из середины каталога доступны только последующие остановки.

Время осмотра — настройки каталога, а не результат маршрутизатора. Маршрут предполагает осмотр
снаружи: музеи, кафе, очереди и расписание транспорта не включены. Сетевой расчёт учитывает
карту дорожной сети, но не гарантирует отсутствие перекрытий или доступ внутрь дворов.
Координаты взяты из опубликованных карточек мест, а не проверены на местности как конкретные входы.
Первая прогулка нужна и для полевой проверки этих точек; при необходимости уточни координаты в каталоге.
Здесь нет пошаговой навигации или линии пути на карте: матрица даёт только переходы и время.

## Как устроен RAG

RAG = retrieval (найти материал) → augmentation (поместить его в контекст) → generation (создать ответ).

1. `app/tour_data/grodno.json`: восемь мест и восемь коротких пересказов источников.
   У каждого фрагмента есть `id`, `place_id`, текст, заголовок и ссылка. Дата подготовки — 30.10.2026.
   Это небольшая стартовая база, не полный исторический справочник. Тексты страниц целиком не копируются.
2. `StoryRetriever` в `app/storytelling.py` сначала отбирает документы по точному месту,
   затем ранжирует их по пересечению слов вопроса и фрагмента. Возвращает максимум три фрагмента.
   Сейчас по одному на место; ранжирование станет полезнее после добавления новых фрагментов.
3. В отдельный запрос OpenRouter передаются вопрос и найденные документы. Инструкция разрешает
   только факты источников и требует признать отсутствие ответа, если материала недостаточно.
4. Модель возвращает JSON с абзацами и ID источников. Python проверяет структуру и ID,
   а реальные URL подставляет из каталога. Придуманные ID и некорректный JSON не публикуются как рассказ.

Это лексический RAG, без embeddings и дополнительной векторной БД. Он позволяет изучить границы
ответственности harness на маленькой базе. Проверка ID обеспечивает происхождение ссылок,
но не доказывает истинность каждого предложения модели: семантические ошибки всё ещё возможны.
Следующее улучшение — больше первичных источников, небольшие тематические фрагменты,
семантический поиск и проверка того, действительно ли ответ подтверждается найденным материалом.

## Что проверить вручную

1. `/places` показывает все восемь мест в нужном порядке.
2. `/walk 120` возвращает расчёт ORS; сумма переходов, осмотра и запаса не превышает 120 минут.
3. `/walk 60 return` показывает укороченный маршрут и обратный переход в общем бюджете.
4. «Расскажи про Старый замок» отвечает со ссылкой на источник.
5. Вопрос о сегодняшней цене билета получает сообщение о недостатке данных.
6. `/today` и подготовка встречи работают как раньше.

Без ORS_API_KEY внешнюю маршрутизацию проверить нельзя. Синтетическая матрица в проверках
подтверждает только корректность алгоритма, не реальную длительность прогулки по Гродно.
